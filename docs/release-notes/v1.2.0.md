## Highlights: ES investigations

Enterprise Security 8 groups findings into investigations. The app now shows them and works with them; it never
changes an investigation except by adding a Note.

### In the list
- New **Investigation** column: the investigation the finding is in (ES-00001 …, *+n* when it is in several), and an
  **Investigation** filter (in an investigation, not in one, or one investigation).
- **Agreement rate**: the analyst's decision is the finding's own disposition; when that is still *Undetermined*, the
  disposition of an investigation that contains the finding is used. Such rows are marked *investigation* in the
  *Analyst* column.
- Read through ES's own lookups (`mc_findings_lookup`, `mc_investigations_lookup`), in the new macro
  `jev_investigations`: no extra REST calls for the list.

### In the detail pane
- The investigations of the finding: ID (a link to the investigation in ES), name, status, owner and disposition.
- **Write summary to the investigation**: the results of all findings in the investigation as one Note on it —
  number of findings, highest suggested urgency, suggested dispositions, the findings suggested as true positive
  (with their entities), undetermined findings, findings not triaged yet, findings where the ES AI SOC Analyst
  disagrees, and findings whose result was moved away from a true positive by analyst statements.
  *Add an LLM summary* adds a short text written by the LLM from the stored facts and results. The same summary is
  not written twice while the results have not changed.
- **Write Note to**: the suggestion Note can go to the finding (as before) or to an investigation that contains it.
- Findings of the investigation that were not triaged yet are only counted by default. On
  **Setup > Investigation summary** an admin can have them triaged first (up to 20 per summary by default).

### Commands
- `| jevinvestigation id=<ES-00001 | GUID> [note=true] [llm=true] [untriaged=count|run] [force=true] [lang=en|ja]`
- `jevnote target=<ES-00001 | GUID>`: write the suggestion Note on an investigation that contains the finding.

### Smaller changes
- The decision model still judges each finding on its own facts: investigations are not sent to it.
- New settings `[investigation] untriaged = count | run` and `max_run = 20`; new KV store collection
  `jev_investigation_notes` (last summary per investigation).

## Upgrade from 1.1.x
Apps > Manage Apps > *Install app from file* > `second_opinion_triage-1.2.0.spl`, tick *Upgrade app*
(Splunk Cloud: Apps > Upload app). Nothing to configure; settings and results are kept.

To see and summarize investigations, users need an ES role that can read and edit investigations
(for example `ess_analyst`) besides `jev_triage_user`. Without it the investigation fields stay empty.

## Requirements
- Splunk Enterprise 10.x with ES 8.7, or Splunk Cloud with ES 8.7.
- A key for the decision model (TypeSafe Jev by default) and, for explanations, translations and LLM summaries, an
  LLM key — your own keys, billed by those providers.

## Tested on
- Splunk Enterprise 10.4.2 + ES 8.7.1: investigations with one and two findings, as an admin and as an analyst
  (`ess_analyst` + `jev_triage_user`): list, filter, agreement rate with an investigation disposition, summary
  (count only, triage first, with an LLM summary), Note to the investigation.

## Known limitations
- The ES AI verdict of the investigation itself is not used, only the verdicts of its findings.
- The triage list runs ES's `notable` macro over all findings in the time range and can take about 10 s on a large
  Splunk Cloud stack.
- Threat intelligence matches cover source IP addresses only.

## 主な変更: ES の調査（Investigation）

Enterprise Security 8 では Finding を調査（Investigation）にまとめます。アプリが調査を表示し、扱えるようになりました。
調査に対しては Note を書くだけで、ほかは変えません。

### 一覧
- 新しい **調査** の列: Finding が入っている調査（ES-00001 など。複数のときは *+n*）。**調査** での絞り込み（調査に入っている・
  入っていない・調査ごと）。
- **一致率**: アナリストの判断は Finding 自身の Disposition です。それがまだ Undetermined のときは、Finding が入っている調査の
  Disposition を使います。その行は「アナリスト」列に「調査」の印が付きます。
- ES のルックアップ（`mc_findings_lookup`、`mc_investigations_lookup`）から新しいマクロ `jev_investigations` で読みます。
  一覧のための REST の呼び出しは増えません。

### 詳細ペイン
- Finding が入っている調査: ID（ES の調査へのリンク）、名前、状態、担当者、Disposition。
- **調査のまとめを書く**: 調査内のすべての Finding の結果を1つの Note にして調査に書きます。内容は Finding の件数、最も高い
  Urgency（提案）、Disposition（提案）の内訳、TP と提案した Finding（対象付き）、判別不可の件数、未トリアージの件数、
  ES AI SOC Analyst と食い違う件数、申告で TP から結果が変わった件数です。*LLM のまとめを含める* にすると、保存した事実と
  結果から LLM が短い文章を書き添えます。結果が変わらないうちは同じまとめを二度書きません。
- **Note の書き先**: 提案の Note を、これまでどおり Finding に書くか、Finding が入っている調査に書くかを選べます。
- 調査内のまだトリアージしていない Finding は、既定では件数だけを数えます。管理者は **Setup > 調査のまとめ** で、先に
  トリアージするように変えられます（既定では1回 20件まで）。

### コマンド
- `| jevinvestigation id=<ES-00001 | GUID> [note=true] [llm=true] [untriaged=count|run] [force=true] [lang=en|ja]`
- `jevnote target=<ES-00001 | GUID>`: 提案の Note を、Finding が入っている調査に書きます。

### 小さな変更
- 判定モデルはこれまでどおり各 Finding をその事実だけで判定します。調査の情報は渡しません。
- 新しい設定 `[investigation] untriaged = count | run`、`max_run = 20`。新しい KV ストア `jev_investigation_notes`
  （調査ごとの最後のまとめ）。

## 1.1.x からのアップグレード
Apps > Manage Apps > *Install app from file* で `second_opinion_triage-1.2.0.spl` を選び、*Upgrade app* にチェック
（Splunk Cloud では Apps > Upload app）。設定は不要で、設定と結果はそのまま残ります。

調査を表示してまとめを書くには、`jev_triage_user` に加えて、調査を読み書きできる ES のロール（例: `ess_analyst`）が
必要です。ないときは調査の欄が空になります。

## 動作環境
- Splunk Enterprise 10.x ＋ ES 8.7、または Splunk Cloud ＋ ES 8.7。
- 判定モデルのキー（既定は TypeSafe Jev）と、説明・翻訳・LLM のまとめを使う場合は LLM のキー（ご自身のキー、各社の料金）。

## 検証した環境
- Splunk Enterprise 10.4.2 ＋ ES 8.7.1: Finding が1件・2件の調査で、管理者とアナリスト（`ess_analyst` ＋ `jev_triage_user`）:
  一覧、絞り込み、調査の Disposition を使った一致率、まとめ（件数のみ・先にトリアージ・LLM のまとめ付き）、調査への Note。

## 既知の制限
- 調査そのものに付く ES AI の判定は使わず、調査内の各 Finding の判定を使います。
- トリアージ一覧は期間内のすべての Finding に ES の `notable` マクロを流すため、大きな Splunk Cloud では約 10 秒かかります。
- 脅威インテリジェンスの照合は送信元 IP アドレスだけです。
